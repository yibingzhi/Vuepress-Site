本文以 **Redis 7.x** + **Spring Boot 3.4.x** + **Redisson 3.3x** 为参考栈。分布式锁与缓存方案对 Redis 版本、主从切换策略敏感，生产务必在**真实故障场景**（主从切换、网络分区）下压测验证，不要只信"文档说可行"。
:::

## 1. 问题背景

微服务中常见两类需求：

1. **分布式锁**：库存扣减、订单号生成、定时任务互斥——同一时刻只有一个实例执行。
2. **缓存一致性**：DB 与 Redis 数据不一致、脏读、缓存击穿/穿透。

二者常一起出现：先查缓存 → 未命中加锁 → 回源 DB → 写缓存。实现顺序错误会导致双写不一致或死锁。

## 2. Redis 分布式锁：SET NX EX

### 2.1 基础命令

```redis
SET lock:order:10086 <uuid> NX EX 30
```

| 参数 | 含义 |
|------|------|
| `NX` | 仅当 key 不存在时设置（Not eXists） |
| `EX 30` | 30 秒过期，防止持有者崩溃导致死锁 |
| value | 唯一标识（UUID），释放时校验，避免删别人的锁 |

### 2.2 Java 原生实现（Lettuce）

```java
@Service
@RequiredArgsConstructor
public class RedisLockService {

    private final StringRedisTemplate redis;

    public boolean tryLock(String key, String token, Duration ttl) {
        Boolean ok = redis.opsForValue().setIfAbsent(key, token, ttl);
        return Boolean.TRUE.equals(ok);
    }

    public void unlock(String key, String token) {
        // Lua：原子比较 value 再删除
        String script = """
                if redis.call('get', KEYS[1]) == ARGV[1] then
                    return redis.call('del', KEYS[1])
                else
                    return 0
                end
                """;
        redis.execute(
                new DefaultRedisScript<>(script, Long.class),
                List.of(key),
                token
        );
    }
}
```

### 2.3 使用模板

```java
String lockKey = "lock:stock:" + skuId;
String token = UUID.randomUUID().toString();
if (!lockService.tryLock(lockKey, token, Duration.ofSeconds(10))) {
    throw new BusinessException("系统繁忙，请重试");
}
try {
    deductStock(skuId, qty);
} finally {
    lockService.unlock(lockKey, token);
}
```

### 2.4 基础实现的局限

| 风险 | 说明 |
|------|------|
| 主从切换 | 主节点写入锁后宕机，从节点未同步，另一客户端可再次加锁 |
| 锁过期 | 业务执行超过 TTL，锁被释放后其他线程进入 |
| 不可重入 | 同一线程重复加锁会失败 |

**缓解**：Redisson 看门狗续期、RedLock 多节点（争议较大）、或改用 **Zookeeper / etcd** 强一致场景。

## 3. Redisson 简要用法

Redisson 封装可重入锁、读写锁、信号量，并提供 **watchdog** 自动续期（默认 30s，每 10s 续一次）。

```xml
<dependency>
    <groupId>org.redisson</groupId>
    <artifactId>redisson-spring-boot-starter</artifactId>
    <version>3.37.0</version>
</dependency>
```

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
```

```java
@Service
@RequiredArgsConstructor
public class InventoryService {

    private final RedissonClient redisson;

    public void deduct(Long skuId, int qty) {
        RLock lock = redisson.getLock("lock:stock:" + skuId);
        boolean acquired = false;
        try {
            // waitTime=3s, leaseTime=-1 启用看门狗
            acquired = lock.tryLock(3, -1, TimeUnit.SECONDS);
            if (!acquired) {
                throw new BusinessException("库存操作冲突");
            }
            doDeduct(skuId, qty);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new BusinessException("加锁中断");
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

**读写锁**（读多写少缓存重建）：

```java
RReadWriteLock rw = redisson.getReadWriteLock("rw:product:" + id);
RLock readLock = rw.readLock();
RLock writeLock = rw.writeLock();
```

## 4. Cache-Aside（旁路缓存）模式

最常用、最易理解的策略：

```
读：先查缓存 → 未命中查 DB → 写入缓存
写：先更新 DB → 再删除缓存（推荐）或更新缓存
```

```java
public Product getProduct(Long id) {
    String key = "product:" + id;
    String cached = redis.opsForValue().get(key);
    if (cached != null) {
        return JsonUtils.fromJson(cached, Product.class);
    }
    Product product = productMapper.selectById(id);
    if (product != null) {
        redis.opsForValue().set(key, JsonUtils.toJson(product), Duration.ofMinutes(30));
    }
    return product;
}

@Transactional
public void updateProduct(Product product) {
    productMapper.updateById(product);
    redis.delete("product:" + product.getId());
}
```

**为什么写操作用"删缓存"而非"更新缓存"？**

- 两次并发写可能导致缓存与 DB 长期不一致。
- 删除后下次读自然回源，逻辑简单。

## 5. 延迟双删（Delayed Double Delete）

解决"删缓存 → 读旧数据写回缓存"的竞态：

```
时间线问题：
T1 线程 A 更新 DB
T2 线程 A 删除缓存
T3 线程 B 读缓存 miss，读 DB（旧值），写回缓存  ← 脏数据
```

**延迟双删**：更新 DB 后删一次；**延迟几百毫秒**再删一次，清理 T3 可能写入的脏缓存。

```java
@Transactional
public void updateWithDelayedDoubleDelete(Product product) {
    String key = "product:" + product.getId();

    productMapper.updateById(product);
    redis.delete(key);

    // 异步延迟二次删除
    delayedExecutor.schedule(() -> redis.delete(key), 500, TimeUnit.MILLISECONDS);
}
```

| 要点 | 建议 |
|------|------|
| 延迟时间 | 大于一次读 DB + 写缓存的 P99，通常 300ms~1s |
| 线程池 | 使用有界队列，避免堆积 |
| 局限 | 仍非强一致，只是降低概率 |

## 6. 与分布式锁结合的"安全读穿"

热点 key 失效时，大量请求打到 DB（缓存击穿）。可用锁控制**只有一个线程**回源：

```java
public Product getProductSafe(Long id) {
    String key = "product:" + id;
    String cached = redis.opsForValue().get(key);
    if (cached != null) {
        return JsonUtils.fromJson(cached, Product.class);
    }

    String lockKey = "lock:cache:" + id;
    RLock lock = redisson.getLock(lockKey);
    try {
        if (lock.tryLock(2, 5, TimeUnit.SECONDS)) {
            // double-check
            cached = redis.opsForValue().get(key);
            if (cached != null) {
                return JsonUtils.fromJson(cached, Product.class);
            }
            Product product = productMapper.selectById(id);
            if (product != null) {
                redis.opsForValue().set(key, JsonUtils.toJson(product), Duration.ofMinutes(30));
            }
            return product;
        }
        // 未拿到锁：短暂等待后重试读缓存
        Thread.sleep(50);
        return getProductSafe(id);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        return productMapper.selectById(id);
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

## 7. Canal / Binlog 订阅（可选）

写路径复杂、多服务改同一数据时，**删缓存**可能遗漏。通过订阅 MySQL binlog（Canal、Debezium）异步失效缓存：

```
MySQL ──binlog──► Canal ──MQ──► 缓存失效消费者 ──► DEL product:123
```

**优点**：业务代码与缓存解耦，覆盖直连 DB 的变更。  
**缺点**：架构复杂、有秒级延迟；需处理消息重复（见幂等）。

```java
@RocketMQMessageListener(topic = "canal-product")
public class ProductCacheInvalidator implements RocketMQListener<String> {
    @Override
    public void onMessage(String body) {
        CanalMessage msg = parse(body);
        if ("product".equals(msg.getTable()) && msg.isUpdateOrDelete()) {
            redis.delete("product:" + msg.getPkValue());
        }
    }
}
```

## 8. 幂等性

分布式锁与 MQ 消费常配合**幂等**：

```java
// 订单支付回调：唯一业务键 + Redis SET NX
public boolean idempotentProcess(String orderNo, Runnable action) {
    String key = "idem:pay:" + orderNo;
    Boolean first = redis.opsForValue().setIfAbsent(key, "1", Duration.ofDays(7));
    if (!Boolean.TRUE.equals(first)) {
        return false; // 已处理
    }
    action.run();
    return true;
}
```

数据库层可用唯一索引（`order_no`）作为最终兜底。

## 9. 什么时候不要用分布式锁？

| 场景 | 更合适的方案 |
|------|-------------|
| 数据库单行更新 | `UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty >= 1` |
| 全局顺序号 | DB 序列、Snowflake、号段模式 |
| 高吞吐计数 | Redis `INCR`、异步聚合 |
| 跨服务长事务 | Saga / TCC，而非长时间持锁 |
| 强一致金融账务 | 数据库事务 + 乐观锁，锁粒度尽量小 |
| 主从 Redis 极端一致 | Zookeeper、etcd、或 Redis Redlock（需评估） |

**原则**：锁的持有时间越短越好；能用水位 SQL 乐观锁就不用分布式锁。

## 10. 方案选型速查

| 需求 | 推荐 |
|------|------|
| 简单互斥、可接受极小概率失效 | `SET NX EX` + Lua 解锁 |
| 生产级可重入、续期 | Redisson |
| 读多写少缓存 | Cache-Aside + 写后删缓存 |
| 高并发热点 key | 逻辑过期 / 互斥锁重建 / 多级缓存 |
| 多源写 DB、缓存难维护 | Canal + 失效消息 |
| 支付/回调 | 幂等键 + 唯一索引 |

---

## 11. 排查不一致的 checklist

1. 是否先删缓存再写 DB？（错误顺序）
2. 缓存 TTL 内 DB 已变，是否有失效机制？
3. 是否存在序列化差异（LocalDateTime 时区）导致"看起来不一致"？
4. 主从延迟：读从库 + 写后读缓存是否读到旧 DB？
5. 事务提交前就删缓存，其他线程读到旧 DB 并回填？
