::: tip 核心结论
分布式消息系统多为 **At-Least-Once** 投递，消费者必须 **幂等**。跨服务一致性优先 **最终一致性**（Outbox / 本地消息表 / Saga），避免强分布式两阶段提交。
:::

## 一、消息投递语义

| 语义 | 含义 | 典型实现 |
|------|------|----------|
| At-Most-Once | 最多一次，可能丢 | 先 ack 再处理 |
| At-Least-Once | 至少一次，可能重复 | 先处理再 ack，失败重试 |
| Exactly-Once | 精确一次 | 端到端极难，常指「幂等 + At-Least-Once」 |

Kafka、RabbitMQ、RocketMQ 默认生产侧重试 + 消费侧手动 ack 时，整体为 **At-Least-Once**。

```
Producer → Broker → Consumer
              ↑         │
              └─ 重试 ──┘（网络抖动、消费失败）
```

**业务目标：** 在 At-Least-Once 前提下，通过幂等与去重达到 **业务上的 Exactly-Once 效果**。

---

## 二、为什么需要幂等

```java
// ❌ 非幂等：重复消费会重复扣款
@RabbitListener(queues = "payment.notify")
public void onPayment(PaymentMessage msg) {
    accountService.credit(msg.getUserId(), msg.getAmount());
}
```

同一条 `paymentId=PAY-001` 消息投递两次 → 用户余额多加一次。

幂等定义：同一业务操作执行多次，**结果与执行一次相同**。

## 三、幂等消费者实现模式

### 3.1 唯一业务键 + 数据库唯一约束

```sql
CREATE TABLE payment_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    payment_id VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    amount DECIMAL(12,2) NOT NULL,
    status VARCHAR(32) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_payment_id (payment_id)
);
```

```java
@Service
@RequiredArgsConstructor
public class PaymentConsumer {

    private final PaymentRecordMapper paymentRecordMapper;

    @Transactional(rollbackFor = Exception.class)
    public void handle(PaymentMessage msg) {
        try {
            paymentRecordMapper.insert(PaymentRecord.from(msg));
            accountService.credit(msg.getUserId(), msg.getAmount());
        } catch (DuplicateKeyException e) {
            log.info("重复消息已忽略 paymentId={}", msg.getPaymentId());
            // 视为成功，正常 ack
        }
    }
}
```

### 3.2 幂等表（去重表）

```sql
CREATE TABLE idempotent_consumer (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    consumer_group VARCHAR(64) NOT NULL,
    message_id VARCHAR(128) NOT NULL,
    processed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_group_msg (consumer_group, message_id)
);
```

```java
@Transactional
public boolean tryProcess(String consumerGroup, String messageId, Runnable action) {
    int inserted = idempotentMapper.insertIgnore(consumerGroup, messageId);
    if (inserted == 0) {
        return false; // 已处理
    }
    action.run();
    return true;
}
```

### 3.3 状态机 CAS

```java
// 订单状态仅允许 PENDING → PAID 一次
int updated = orderMapper.updateStatus(
    orderId, OrderStatus.PENDING, OrderStatus.PAID);
if (updated == 0) {
    log.warn("订单状态已变更，跳过重复支付 orderId={}", orderId);
    return;
}
```

适合有明确状态流转的业务。

### 3.4 分布式锁（慎用）

```java
String lockKey = "pay:" + msg.getPaymentId();
if (!redisLock.tryLock(lockKey, 30, TimeUnit.SECONDS)) {
    return;
}
try {
    if (paymentExists(msg.getPaymentId())) return;
    processPayment(msg);
} finally {
    redisLock.unlock(lockKey);
}
```

锁不能替代持久化去重记录；锁过期仍可能重复，需与 DB 唯一键组合。

### 3.5 消息 ID 选择

| 来源 | 示例 |
|------|------|
| 业务 ID | `orderNo`、`paymentId` |
| Broker MessageId | Rabbit `messageId`、Kafka offset+partition（不推荐单独作业务幂等键） |
| 自定义 | UUID 写入消息头 `X-Idempotency-Key` |

**推荐：** 业务主键优先，与消息中间件 ID 解耦。

## 五、Outbox 模式

**问题：** 数据库事务提交与消息发送无法原子一致。

```
❌ 先 DB 提交再发 MQ → DB 成功 MQ 失败 → 消息丢失
❌ 先发 MQ 再 DB → MQ 成功 DB 失败 → 脏消息
```

**Outbox：** 业务与「待发送消息」在同一本地事务写入；独立 **Relay** 进程轮询并发布到 MQ。

```
┌─────────────┐     同一事务      ┌──────────────┐
│ 业务表       │ ◄──────────────► │ outbox 表     │
└─────────────┘                  └──────┬───────┘
                                        │ Relay 轮询
                                        ▼
                                 ┌──────────────┐
                                 │ Kafka/Rabbit │
                                 └──────────────┘
```

### 5.1 表结构

```sql
CREATE TABLE outbox_event (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    aggregate_type VARCHAR(64) NOT NULL,
    aggregate_id VARCHAR(64) NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    payload JSON NOT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'NEW',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    published_at TIMESTAMP NULL,
    KEY idx_status_created (status, created_at)
);
```

### 5.2 业务写入

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderMapper orderMapper;
    private final OutboxMapper outboxMapper;

    @Transactional
    public Order createOrder(CreateOrderCommand cmd) {
        Order order = Order.create(cmd);
        orderMapper.insert(order);

        OutboxEvent event = OutboxEvent.builder()
            .aggregateType("Order")
            .aggregateId(order.getOrderNo())
            .eventType("OrderCreated")
            .payload(JsonUtils.toJson(OrderCreatedEvent.from(order)))
            .build();
        outboxMapper.insert(event);

        return order;
    }
}
```

### 5.3 Relay 发布

```java
@Scheduled(fixedDelay = 1000)
public void publishPendingEvents() {
    List<OutboxEvent> events = outboxMapper.selectByStatus("NEW", 100);
    for (OutboxEvent event : events) {
        try {
            kafkaTemplate.send("order-events", event.getAggregateId(), event.getPayload());
            outboxMapper.markPublished(event.getId());
        } catch (Exception e) {
            log.error("publish failed id={}", event.getId(), e);
            // 下次重试；消费端仍需幂等
        }
    }
}
```

### 5.4 与 Debezium CDC

Outbox 表变更可由 Debezium 捕获 → Kafka，省去自研 Relay，适合大数据量。

## 六、本地消息表（Transactional Local Message Table）

与 Outbox 思想相同，早期阿里方案常用命名 **本地消息表**：

| 字段 | 说明 |
|------|------|
| message_id | 全局唯一 |
| topic | 目标队列 |
| body | 消息体 |
| status | NEW / SENT / CONFIRMED |
| retry_count | 重试次数 |

定时任务扫描 `status=NEW` 发送，成功后更新；下游确认后 `CONFIRMED`（可选）。

**与 Outbox 区别：** Outbox 强调领域事件；本地消息表更偏技术表，二者可合并实现。

## 七、最终一致性

强一致性（2PC/XA）性能差、可用性低；微服务普遍接受 **最终一致性**：

> 系统在一段时间后达到一致，中间存在短暂不一致窗口。

### 7.1 一致性的层次

```
订单服务: 订单已创建 ──事件──► 库存服务: 扣减库存
                              积分服务: 加积分
```

允许秒级延迟；用户看到「处理中」状态。

### 7.2 对账与补偿

- 定时对账任务比对订单 vs 库存流水
- 不一致时告警 + 人工/自动补偿

```java
@Scheduled(cron = "0 0 2 * * ?")
public void reconcile() {
    List<String> orphanOrders = reconciliationService.findPaidWithoutInventory();
    orphanOrders.forEach(this::compensateOrAlert);
}
```

## 八、Saga 模式（简要）

长事务拆为本地事务 + 补偿步骤。

### 8.1 Choreography（编排式，事件驱动）

```
OrderCreated → InventoryReserved → PaymentCompleted
                    ↓ 失败
              InventoryReleased（补偿事件）
```

各服务监听事件自行反应；简单场景够用，链路复杂时难追踪。

### 8.2 Orchestration（编排式，中心协调器）

```
Saga Orchestrator
  1. 调用库存 reserve
  2. 调用支付 pay
  3. 失败 → 调用库存 release
```

```java
public class CreateOrderSaga {

    public void execute(CreateOrderContext ctx) {
        try {
            inventoryClient.reserve(ctx);
            paymentClient.pay(ctx);
            orderService.markCompleted(ctx.getOrderId());
        } catch (Exception e) {
            compensate(ctx);
            throw e;
        }
    }

    private void compensate(CreateOrderContext ctx) {
        try {
            inventoryClient.release(ctx);
        } catch (Exception ex) {
            log.error("补偿失败，需人工介入 orderId={}", ctx.getOrderId(), ex);
        }
    }
}
```

框架：Seata Saga、Temporal、Camunda。

### 8.3 Saga vs TCC vs Outbox

| 模式 | 一致性 | 复杂度 | 适用 |
|------|--------|--------|------|
| Outbox + 事件 | 最终一致 | 中 | 单向通知、解耦 |
| Saga | 最终一致 | 高 | 多步业务流程 |
| TCC | 准实时 | 很高 | 金融强一致场景 |

## 九、RabbitMQ 消费者 Ack 与幂等

```java
@RabbitListener(queues = "order.created")
public void onMessage(OrderCreatedEvent event, Channel channel,
                      @Header(AmqpHeaders.DELIVERY_TAG) long tag) {
    try {
        if (!idempotentService.tryProcess("order-consumer", event.getEventId())) {
            channel.basicAck(tag, false);
            return;
        }
        inventoryService.reserve(event);
        channel.basicAck(tag, false);
    } catch (BusinessException e) {
        // 不可重试，进死信
        channel.basicNack(tag, false, false);
    } catch (Exception e) {
        // 可重试
        channel.basicNack(tag, false, true);
    }
}
```

Spring AMQP 默认 `auto` ack；生产建议 **manual ack** + 幂等。

## 十、Kafka 消费者幂等

```java
@KafkaListener(topics = "order-events", groupId = "inventory-service")
public void consume(ConsumerRecord<String, String> record) {
    OrderCreatedEvent event = JsonUtils.fromJson(record.value(), OrderCreatedEvent.class);
    String idempotencyKey = event.getOrderNo() + ":" + event.getEventType();

    if (!idempotentService.tryProcess("inventory-service", idempotencyKey)) {
        return;
    }
    inventoryService.reserve(event);
}
```

注意：

- 消费失败抛异常触发 rebalance 重试
- `enable.auto.commit=false` + 处理成功后 commit
- 幂等键不要用 `partition+offset`（重放 topic 时变化）

## 十一、事务消息（RocketMQ 简要）

RocketMQ **事务消息**：半消息 → 本地事务执行 → commit/rollback 消息。

```
Producer                         Broker                    Consumer
   │ send half msg ──────────────►│
   │ execute local TX             │
   │ commit/rollback ────────────►│ 可见消息 ───────────────►│
```

适合订单创建与消息发送原子性；其他 MQ 可用 Outbox 等价实现。

## 十二、设计 checklist

### 12.1 消息设计

- [ ] 每条消息含 `eventId` / 业务唯一键
- [ ] 消息体版本化（`schemaVersion`）
- [ ] 敏感字段加密

### 12.2 消费端

- [ ] 幂等表或业务唯一约束
- [ ] 消费与写库同一事务（或先占幂等槽再处理）
- [ ] 区分可重试与不可重试异常
- [ ] 死信队列 + 告警

### 12.3 生产端

- [ ] Outbox 或事务消息
- [ ] 发送失败重试 + 指数退避
- [ ] 消息顺序：同一 `aggregateId` 用同一分区键

## 十三、完整流程示例：下单扣库存

```
1. OrderService @Transactional
   - INSERT orders
   - INSERT outbox (OrderCreated)

2. OutboxRelay
   - READ outbox NEW
   - PUBLISH order-events
   - UPDATE outbox PUBLISHED

3. InventoryService @Transactional
   - INSERT idempotent (group, eventId) — 幂等
   - UPDATE inventory SET qty = qty - n
   - INSERT inventory_log

4. 失败重试
   - 步骤 3 重复 → DuplicateKey → ack 跳过

5. 对账 Job（T+1）
   - 订单 PAID 但无库存流水 → 告警
```

## 十四、常见反模式

| 反模式 | 后果 |
|--------|------|
| 仅靠 Redis SETNX 无持久化 | Redis 丢数据后重复消费 |
| 先 ack 再处理 | At-Most-Once，消息丢失 |
| 幂等键用随机 UUID | 无法去重 |
| 大事务包含 RPC | 持锁长、不一致窗口大 |
| 无死信队列 | 毒消息阻塞队列 |
